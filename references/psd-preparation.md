# PSD 整理与样例

在分析、命名、调整画布或比较整理前后 PSD 时读取。

## 源更新先审核差异

源 PSD 更新时，先只读对比新源 PSD 与当前固定 `_UI`，结合原 `01-PSD修改说明.md` 的命名、分组、隐藏层处理和人工修正记录解释差异；可取得旧源版本时同时核对。不能把源与整理稿固有的加工差异全部认作新设计变化。把具体增删、视觉/文本/效果变化、拟保留修正及拟更新项写入当前说明，提交用户审核。用户同意本次差异后，才修改固定 `_UI` 并继续导出；一般性的“更新界面”请求不替代这次审核。已审核范围未变时后续不重复询问；源文件再次变化则复核新增差异。

用户只修改 `_UI` 并要求续作时仍按修正版检查入口执行，不误当成源更新。

## 源文件与输出命名

开始修改前记录本次输入 PSD/PSB 的路径和 SHA-256，完整保留源设计稿；后续整理只作用于当前约定的 `_UI` 工作稿。保存后再次计算源稿摘要，确认源文件没有被改写。文件指纹用于识别版本，不能替代可恢复的实际文件。

- 用户指定输出文件名时采用指定名称，并确保整理输出不覆盖源设计稿；未指定名称时采用用途后缀 `_UI`，例如 `BattleHUD.psd` → `BattleHUD_UI.psd`。PSB 沿用 `.psb`。
- 既有链条固定使用当前约定的 `_UI` 路径。新源稿更新时，完成上述差异审核后，先保留旧 `_UI` 的可恢复版本及原说明，再把新整理结果更新到该路径；不默认新增带时间戳的 `_UI` 作为另一份当前输入。备份位置遵守项目任务归档约定，并在原说明内关联。
- 目标已有文件时，先确认它是否属于本界面的整理链条；若是无关文件或目标与源设计稿实际为同一文件，先解决路径冲突，不能静默覆盖。用户直接提供 `_UI` 修正版时，以该保存稿续作；需进一步改写则先保留可恢复版本，只修改授权项，不重复追加 `_UI` 后缀。
- 同一轮继续保存和后续维护均使用已核实的当前工作稿。纯读取或直接使用已有稿生成 Prefab 时不制造额外 PSD。原稿与工作稿用途明确，不能让用户查看的固定 `_UI` 停在旧版，却把另一文件的导出结果作为交付。
- 文件名中的 `_UI` 只标识设计稿用途；Prefab 名、模块名、C# 类型名和导出路径单独按项目约定确定，不直接由 PSD 文件名追加后缀。

按 [阶段溯源记录](traceability.md) 建立或维护同一份固定的 `01-PSD修改说明.md`，新源稿只追加处理记录，不新增同类 MD。只记录变化项并写清原因，所有未执行的检查标为未执行；不能用模板的预期结果代替实际验证。

## 导出前整理稿检查

每次输出视觉 Prefab、临时 Prefab 或执行重导入验证前，检查本次实际使用的 PSD/PSB。该步骤是 Agent 的执行判断，不新增固定人工确认点，也不表示已安装文件监听器或自动差异合并工具。

1. **核对输入与已记录版本。** 读取当前整理稿及原 `01-PSD修改说明.md`，核对路径、SHA-256、保存状态和已有结构/视觉证据；确认用户查看的当前 `_UI`、导入器实际输入与记录版本一致。指纹只能说明文件是否变化，不能识别作者、修改项或理由；不能只按文件名或时间戳选择版本。没有旧证据时检查当前稿，记录历史未知，不编造差异，也不只因缺少历史而阻止可验证的导出。
2. **识别实际修正。** 版本变化时，对照可用的旧记录、图层盘点和预览，检查命名、分组、层级/类型、Item 边界、图层增删、文字、位置尺寸、可见性及效果变化。以结构与视觉共同确认；解析工具未覆盖的属性需通过可靠编辑/预览通道检查。用户明确已修正时，以当前保存稿为本轮依据；仅检测到变化而无法确定意图时，先查证，必要时只询问不明确项。
3. **校验可导出性。** 检查本次画布约定、素材和字体、蒙版/效果、导入指令、切图路径冲突、绑定命名与 Item 作用域。不要求修正版符合 Agent 上次的分组偏好；符合当前需求与工具约束就继续。发现会导致导出失败、引用冲突、关键视觉丢失或意图不明的问题时，列明具体图层、影响和建议，待用户决定后处理相关项，不自动改回旧规则。已有明确授权的修复无需重复确认。
4. **保留并记录。** 在原第一份说明追加人工修正、可核实的前后值、依据、当前指纹及本次检查结果；未知原因写“用户调整，原因未说明”。保留先前被导出使用的版本行。仅要求检查或记录时到此交付，不擅自生成 Prefab。首次缺少说明可建立首份并注明历史未知。
5. **从核验版本继续。** 按实际 PSD 路径和版本调用现有导出方法，核对导出前后输入指纹；期间文件又变化时不能把旧输出当作最新结果，重新检查并按核验版本重新导出。已有正式 Prefab 时，先按维护入口记录其实际适配基线、保留可恢复版本和引用身份，再沿用新建主流程通过原工具生成正式输出，以当前两份说明和旧正式资产快速对比、恢复仍适用的适配并完成绑定。已有明确授权时不因重新生成额外确认；历史版本及旧导出记录保留，不回写成新结果。

源 PSD 的新一轮更新仍从源开始，但先只读核对上一版整理稿与原说明；发现尚未记录的修改时，按可用证据补入原第一份，缺少旧证据则注明历史未知。参考这些修正，在新整理稿中保留仍适用的意图，不能用旧的生成或修正规则机械覆盖新设计。新源与旧修正冲突且无法判断时，只就具体冲突询问。先保留旧 `_UI.psd` 的可恢复版本，再更新当前约定路径，沿用上节规则。

### 反馈生成规则

- 可跨界面复用且有证据支持的生成错误，例如误判 Item 边界、产生非法绑定名，提炼为适用范围明确的 Skill 生成/检查规则，并记录依据与实际落点。不因一次页面修正就扩大成通用限制；规则改进不替代本轮修正版的保留和继续交付。
- 单页分组、命名选择、布局偏好和设计变化只维护该界面的原说明，下次处理该界面时参考，不写成所有 PSD 的默认规则。不把项目专有资源、API 或机器路径复制进通用规则。
- 按已有授权维护个人 Skill；只记录了建议但尚未修改规则时，明确标注“建议/未实施”，不能宣称规则已更新。原因不明确的人工修改先保留事实，不猜测并固化生成限制。

## 盘点脚本

`scripts/inspect_psd.py` 只读 PSD/PSB，输出 UTF-8 JSON。Python 命令和输入、输出路径由当前环境解析；从 Skill 根目录运行的通用示例：

```text
python scripts/inspect_psd.py <源PSD路径> --output <新的图层JSON路径> --preview <新的预览PNG路径>
```

Python 先使用当前环境的 `psd-tools`，或本机缓存 `%LOCALAPPDATA%/CodexTools/python-psd-tools/`；也可通过 `--psd-tools-path` 指定依赖目录。缺失时将 `scripts/requirements.txt` 中的依赖安装到本机缓存或项目允许的外部虚拟环境，不能把第三方包装进 Skill 或 Unity 工程。例如在 PowerShell 中，先将 `$pythonExe` 和 `$skillRoot` 设为当前环境核实的路径：

```powershell
$psdToolRoot = Join-Path $env:LOCALAPPDATA 'CodexTools/python-psd-tools'
& $pythonExe -m pip install --target $psdToolRoot -r (Join-Path $skillRoot 'scripts/requirements.txt')
```

只在依赖缺失或已确认不兼容时安装；已有可用环境直接复用。脚本不自动安装依赖、不写 PSD，也不调用 Photoshop/Unity。输出路径必须是新文件，避免覆盖已有报告或源资源。

预览来自 PSD 内保存的合成图，可能陈旧；它只用于辅助对照。没有合成图时不能把空白图当成预览成功。本次改写 PSD 时检查重新保存后的结构与真实合成结果；本次包含 Unity 交付时另检查 Unity 显示结果。已有整理稿可以只读核验，不为验收而强制重新保存。

## 图层操作映射

每个操作至少标明原图层定位、原名、目标路径、用途、操作和理由。图层 ID 可辅助匹配同一文件的前后版本，但不是跨文件的全局标识；缺失或重复时使用层级索引路径、类型、位置和视觉核对。重组会改变索引，必须基于操作前快照定位对象，避免边遍历边按已变化的索引改名。

| 原图层定位 | 目标路径 | 用途 | 操作 |
|---|---|---|---|
| 原稿中已确认的主背景层 | `bg` | 主背景 | 改名，保持比例 |
| 原稿中已确认的标志层 | `logo` | 标志 | 改名，保留透明边缘 |
| 原稿中的进度槽 | `progress/bg` | 进度条底图 | 分组并改名 |
| 原稿中的进度填充 | `progress/bar_c` | 代码控制的 Image | 分组并添加 XUGUI 组件标记 |
| 原稿中的说明文字 | `tips` | 静态文字 | 改名，保留文本属性 |

上表展示一个加载界面的整理模式；不是所有 PSD 都应该生成这五个元素。填充动画、时长和完成动作属于任务逻辑，不从这个样例继承。

## 尺寸与视觉

- 完整流程未另行指定时，目标画布为 750×1334；采用本次确认的目标尺寸同步调整设计坐标和必要的图层位置，不只修改文件名或 PNG 尺寸。用户只要求改名时保留原尺寸、坐标、分组及图层集合。
- 原稿与目标宽高比接近时，选择统一缩放系数并处理像素取整。比例明显不同时，等比缩放素材、调整画布和布局；不能为凑尺寸把 logo、人物、按钮或字体非等比拉伸。
- 超出画布的背景可能用于覆盖屏幕，不要按 PSD 画布边缘机械裁掉图层像素。记录背景延伸与关键内容可裁切范围。
- 保留文本可编辑性；字体缺失时核对项目字体映射及效果，不擅自栅格化文字或替换文案。
- 蒙版、图层样式、剪贴关系、智能对象和颜色配置会影响最终图像；重组之前先核对依赖，不能仅按矩形位置拼回一张看似相同的图。

## 命名与结构

- 用元素用途命名，禁止将所有图层机械音译或按序号重命名。静态装饰不必全部添加代码绑定后缀。
- PSD 导入指令与代码生成后缀属于两个协议：先核对导入器是否剥离 `/R`、`/SX`、`/SY`、`/T####` 等指令，再检查最终 Unity 节点名。不能因清理字符而破坏效果指令，也不能让指令进入 C# 字段名。
- 对代码绑定节点使用当前生成器支持的合法、唯一名称。PLink 的 `_c`、`_b`、`_g`、`_@` 详见 PLink 参考；其他项目不自动套用。
- 使用功能分组保持进度槽/填充、按钮/文字等元素的相对关系，保持渲染顺序与蒙版关系。
- 不同父节点下同名的静态 `bg` 不一定是错误，但要检查图片导出是否按短名产生路径冲突；生成字段的重名还要按生成作用域单独检查。
- 整理输出时按下节排除关闭小眼睛的图层。小眼睛开启但被其他层遮挡、透明度为零或用途不明确的层，不仅凭这些现象删除；根据当前设计和明确要求确定其他取舍。

### 隐藏图层排除

- 从源稿整理生成 `_UI.psd`（或对应 PSB）时，以操作前保存稿的小眼睛状态为准：图层自身关闭，或任意祖先组关闭，均默认不进入整理输出。隐藏组及其全部子层一起排除；不能因子层自身小眼睛开启而单独捞出，也不因名称像 Item、按钮或状态节点就自动保留。
- 原稿完整保留；允许先复制原稿再从工作副本移除排除项，但最终输出中这些节点应实际不存在，只保持隐藏不算完成。盘点脚本的 `own_visible` 和 `effective_visible` 可作为判断依据，后者是自身与祖先小眼睛状态的合并结果，不代表像素是否实际可见。
- 默认排除不逐项询问。用户明确要求保留某个隐藏层时，才作为例外保留该层和必要的祖先结构，并记录保留范围与可见状态。小眼睛开启但被遮挡、画布外或透明度为零，不属于本规则的隐藏判定。
- 这一步属于整理输出。仅改名任务仍不改变图层集合；直接核验或导出用户已修正的 `_UI.psd` 时不借本规则清理其文件，只有本次确实执行新一轮整理时才应用。不得将规则扩展为删除正式 Prefab 中的隐藏节点或 Item 模板。
- 在原 `01-PSD修改说明.md` 记录排除路径、自身/祖先隐藏原因、涉及数量及用户指定的保留例外。保存后重新打开输出，核对排除节点确实不存在、源文件未变，并检查可见层的剪贴关系、蒙版和效果；隐藏判定不能替代这些视觉检查。

## 编辑与重新打开

优先使用当前可调用、能保留 Photoshop 结构的编辑能力；如 Photoshop 自动化或其脚本通道，先核对实际 API、打开文档和保存目标。仅有只读解析库并不代表具备完整缩放/合成能力。新增编辑脚本要在独立输出副本上验证，再应用到目标输出。

保存前后核对原稿摘要，重新打开输出并检查：画布、图层数量及映射、可见性、文字、图层效果和保存后的真实合成图。不能通过只改 PNG 或手写 Unity 层级来宣称 PSD 已完成整理。

当前环境没有可靠 PSD 编辑通道时，先交付图层盘点和可执行的操作映射，明确“PSD 尚未改写”的阻断；继续完成不依赖该改写的调查工作。不得把未执行的操作写成已完成。
