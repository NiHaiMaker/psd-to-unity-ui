# 已有链条维护

已有界面更新按新建主流程执行：维护固定整理稿，调用项目现成工具输出到正式路径，再依据原说明和导出前实际资产快速对比、恢复仍适用的适配、处理设计差异、完成绑定和验证。源 PSD 更新必须先审核本次设计差异，再更新固定 `_UI`；默认不另建带时间戳的整理稿或强制隔离候选合并。

## 两份 MD 共同驱动迭代

每轮先读取当前两份说明，并贯穿差异审核、PSD 更新、Prefab 处理和代码修复。第一份 `01-PSD修改说明.md` 用于解释源稿与 `_UI` 的命名/分组映射、图层取舍、视觉和人工修正；第二份 `02-Prefab减法与布局说明.md` 用于解释生成节点的减法、Item、布局、适配、绑定与已有功能接入。跨阶段用图层到节点映射关联，不能只按减法表重放，也不能把历史整理差异误当成新增设计。执行后分别更新两份的实际差异、依据和验证状态，并关联本次记录。

## 识别当前状态

关联源 PSD、固定 `<原名>_UI.psd` / `.psb`、正式 Prefab、两份原说明、图片、生成绑定与手写业务代码。检查工作副本状态并保留用户已有改动。明确读取的是保存后的 Prefab、Prefab Stage 还是场景实例；未应用的实例覆盖不等于正式资产，不自动保存无关场景。

同一界面始终维护原 `01-PSD修改说明.md` 和 `02-Prefab减法与布局说明.md`，记录按轮次追加。SHA-256 仅识别版本，不能恢复适配；恢复依据必须包含实际参数、组件、引用或可恢复的资产快照。缺少历史时记录当前实际值和历史未知，不编造旧值。

## 整理稿修正后续作

用户修改固定 `_UI` 后，以当前修正版续作，按 [导出前整理稿检查](psd-preparation.md#导出前整理稿检查) 核验，不重新从源覆盖其修正。源 PSD 本身更新时保留源文件，根据旧整理稿和第一份说明识别仍适用的命名、分组及修订，将新源与当前 `_UI` 的差异结合当前说明中的历史记录分类汇总给用户审核，同意后才维护同一固定 `_UI`。更新前保留必要的可恢复内容；恢复副本只用于恢复，不成为新一轮工作稿或另一个交付版本。

## 源 PSD 更新主流程

**当前差异审核是更新固定 `_UI` 的前置条件。** 先只读比较新源 PSD 与当前 `_UI`，结合当前说明中的历史记录区分新设计差异、历史整理差异和人工修正；不能将二者全部差异当成新设计。总结拟保留、替换、删除及未确定项，说明影响并交用户审核，同意后才写入固定 `_UI`。笼统的“执行完整流程”“直接更新”授权不能替代本次具体差异审核；已经审核的同一差异与范围，后续不重复确认。审核期间可独立补齐恢复基线，但不得提前更新整理稿或执行依赖该更新的正式导出。

1. **补齐当前基线。** 在任何会覆盖正式产物的导出之前，读取原两份说明与当前实际资产，补录尚未记录的人工适配。保存适配所需节点身份、层级、锚点、pivot、位置、尺寸、缩放、布局组件、文本设置、列表配置、模板、必要组件和序列化引用。记录相关 `.meta` / GUID、内部对象及外部引用；可能被生成器覆盖且无法由参数恢复的内容，保留可恢复资产快照。不能只留摘要就开始覆盖。
2. **审核通过后维护固定整理稿。** 记录本次具体差异与用户同意依据，保留源 PSD，在固定 `_UI` 上完成主流程中的整理和导出前检查，维护第一份说明。检查新设计与旧人工修正的真实差异，不机械恢复与新设计冲突的旧值。
3. **调用现成工具正式导出。** 核对真实 Importer、入口、配置和写入范围，沿用正式模块名与路径执行工具菜单、按钮或同一方法。切图、Texture、Atlas、Prefab 均遵循当前工具配置与已授权更新范围，不默认创建新名字或隔离候选。导出前核对共享图片影响，不能因同名就认定可复用；涉及其它界面的共享变化不属于默许范围。工具失败时停止依赖该步骤的写入，报告已写文件和当前状态，保留恢复依据；文件还原由用户处理，不自动回滚。
4. **快速对比并恢复适配。** 比较导出结果与基线、原说明及新设计，恢复仍适用的用户适配、组件和业务接入结构，按新建主流程落实减法、Item 和布局。对新增、删除、变化节点逐项处理，记录保留项、变化及原因；不直接重放过时固定参数。本次差异已审核且后续仍在同一范围时继续执行，不因恢复适配或进入代码阶段重复确认。只有实际冲突无法判断或影响超出授权时，提出具体问题。
5. **生成、修复、编译、刷新。** 调用项目现成 UI 生成工具，修复受本次变化影响的手写业务引用，编译且类型可加载后调用现成刷新入口，再检查实际序列化引用。不要手改生成文件。刷新可能回写根 Canvas/Transform，完成后再次核对适配基线。
6. **旧业务适配及验证。** 代码仅修复受变化影响的旧逻辑；差异属于以前已实现的功能时，补全其对新节点与数据展示的适配，依据现有代码与调用链证明已实现。从未实现的功能不自动补做，记录缺口，不把新增视觉节点当作业务实现授权。验证显示、列表、隐藏重开及受影响功能，审阅差异和引用，追加原第二份说明；区分静态检查、Unity 编译与实际运行验证。

## 正式写入前复核

本节适用于固定 `_UI` 更新、正式导出和后处理；中断恢复或用户同时编辑后重新核对，不替代前述当前差异审核。

- 写入前重读输入与目标，比较基线以来的真实变化。无冲突的新用户设置纳入最新恢复基线，已审核的同一差异范围继续有效；源设计又变化或出现新冲突时，只补审新增差异。
- 保持正式资源名称、路径与 `.meta` / GUID。工具重导出仍可能更换内部对象身份，核对 Sprite 子资源、生成字段、外部序列化引用、动画路径、Prefab 实例及 Variant 覆盖；同名同路径不代表引用必然保留。
- 记录真实恢复来源和字段值，不把 SHA-256 当作可恢复副本。发现无法恢复的既有内容时先补齐证据或说明具体限制。
- 恢复及处理以本次设计和仍适用的用户适配为准，不能把更新请求扩展成无关业务改造或资源迁移。

## 改动较多时重建

完成本次差异审核后，正式工具重导出是本维护主流程的一部分，不因界面已存在而另设重复审批。结构变化较大时，在原说明中记录需要恢复的适配、组件和引用以及实际处理方案，沿用正式名称与路径。若将超出用户授权删除业务能力、改变交互或影响其它界面，只澄清该新增范围；不重复询问已批准的导出与更新。

## 用户直接修改适配

用户已保存的适配是最新基线。只要求记录时，读取实际资产、对照原第二份说明，补录参数和显示检查；未知原因写“用户调整，原因未说明”。不重导出、不重放旧脚本；节点与绑定不变时不重跑绑定、不改业务。后续完整更新先补齐并使用这份新基线。

用户委托 Agent 调整适配时按明确范围执行、验证并记录，不误判成只读观察。仅参数变化且绑定不变时无需生成或刷新。发现实际结构/绑定变化，再执行所需工具步骤。

## 新视觉节点的业务补充边界

以对应业务功能是否存在判断，不以该节点此前是否有专门代码判断。新设计为已有功能增加视觉反馈时，补齐生成绑定后的业务状态、显隐和刷新逻辑，并验证状态切换；这属于已有功能的完整维护，不是擅自扩展新业务。审核差异时就列明这种接入需求。

例如，界面已有条目选中状态，本轮新增选中框，就需要将选中框接入当前选中状态及切换刷新，不能只保留静态图片。相反，头像一直只作展示、没有头像数据或交互业务时，不自动增加头像加载、点击或更换功能。具体页面节点与业务来源记录在该界面的两份 MD 中。

## 仅修改手写功能代码

现有节点和绑定满足需求时，只核对调用链并修改业务逻辑、编译、验证，不导出 PSD、不调整 Prefab、不要求空的资产确认清单。确需节点或绑定变化时按已有授权补齐资产与现成工具流程，不按名称查找兜底，不手改生成文件。

## 工具边界与交付

本 Skill 不得修改框架、PSD 导入器、UI 生成器或其它公共工具源码；不能通过工具修复、替代生成器或自写烘焙切图补足能力。手写代码只允许本次业务逻辑；UI 资产编辑与现成工具调用沿用项目规则。工具缺失或不支持设计效果时，报告具体能力限制与已完成状态，不扩展为框架/导入器开发任务。

Unity 通过项目规定通道操作，PLink 使用 Coplay MCP；不新增工程内辅助工具，不执行未经要求的 SVN 调度。默认只交付固定 `_UI`、正式资源及原两份说明；可恢复快照按项目要求保留，不盲删资产及依赖，不将记录更新当作验证通过。
